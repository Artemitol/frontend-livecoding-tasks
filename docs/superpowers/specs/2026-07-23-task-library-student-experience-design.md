# Дизайн ученического интерфейса базы frontend-задач

Дата: 2026-07-23
Статус: дизайн одобрен в диалоге; письменная спецификация ожидает review
Beads: `frontend-livecoding-tasks-kln-student-redesign-spec`
Предыдущая спецификация: `docs/superpowers/specs/2026-07-22-frontend-task-knowledge-base-design.md`

## 1. Назначение

Эта спецификация перерабатывает ученическую часть существующей Markdown-базы после технического завершения первоначального плана. Текущая библиотека корректна как набор проверенных материалов, но неудобна как учебный продукт:

- корневой README перегружен таблицами и служебной информацией;
- задачу трудно найти иначе чем в одном длинном каталоге;
- карточка повторяет слишком много полей и технических терминов;
- стартовый код часто разделён между секциями или вынесен в `assets/`;
- ученик может потеряться между README и деревом файлов GitHub;
- подсказка слишком быстро сменяется готовым решением;
- ссылки на подходящие онлайн-редакторы не встроены в учебный путь.

Цель — сделать корневой README стартовой страницей, подборки — основным способом выбора, а каждую карточку — коротким самодостаточным упражнением, которое можно скопировать в подходящий онлайн-редактор.

## 2. Отношение к предыдущему дизайну

Предыдущая спецификация остаётся историческим документом первоначального проектирования. Эта спецификация имеет приоритет там, где меняет ученические контракты:

- корневой каталог;
- структуру и содержание карточки;
- обязательные метаданные;
- работу с кодом и текстовыми проверочными данными;
- тематическую классификацию;
- progressive disclosure;
- правила синхронизации ученических ссылок.

Не затронутые решения сохраняются: Markdown-first, одна папка на задачу, стабильные slugs, строгая техническая корректность, оригинальность материалов, Beads как durable tracking и GRACE как инженерный протокол.

## 3. Границы

### Входит в scope

- полная миграция всех 20 существующих карточек;
- новая корневая README-навигация;
- десять тематических подборок;
- три собеседовательные подборки;
- два режима карточки;
- три последовательные подсказки;
- единый copy-ready контракт кода;
- перенос текстовых HTML-проверок из `assets/` в карточки;
- ссылки на четыре онлайн-редактора;
- синхронизация шаблона, правил авторинга, GRACE shared artifacts и verification contracts;
- rendered GitHub review полного ученического пути.

### Не входит в scope

- Docusaurus или другой генератор документации;
- задеплоенное приложение;
- GitHub Pages, Vercel, Netlify и любой deployment pipeline;
- поиск, фильтры и интерактивный каталог;
- новый постоянный runtime, package manager, валидатор или CI;
- создание новых учебных задач;
- изменение учебных целей существующих задач;
- переименование существующих task slugs.

Будущий генератор документации должен подключаться отдельной спецификацией. Текущая структура не должна намеренно блокировать такой переход, но её реализация не является критерием этой работы.

## 4. Архитектура ученического контента

```text
README.md
collections/
  javascript/
    arrays-and-objects/README.md
    this-and-closures/README.md
    event-loop-and-async/README.md
    dom-and-events/README.md
  typescript/
    type-modeling/README.md
    narrowing-and-validation/README.md
  html-css/
    layout/README.md
    accessibility/README.md
  react/
    state-and-derived-data/README.md
    effects-and-lifecycle/README.md
  interviews/
    interview-01/README.md
    interview-02/README.md
    interview-03/README.md
tasks/
  <task-slug>/
    README.md
templates/
  task-template.md
```

Промежуточные README уровня технологии не создаются. Корневой README сразу ссылается на конкретные подборки, визуально группируя их под заголовками JavaScript, TypeScript, HTML/CSS и React.

Каждая задача:

- существует в одном `tasks/<task-slug>/README.md`;
- принадлежит ровно одной тематической подборке;
- входит не более чем в одно собеседование;
- не дублирует содержимое в collection-файлах;
- сохраняет существующий slug и относительный URL.

## 5. Ученический путь и обучение навигации

Основной путь:

```text
корневой README
→ README выбранной подборки
→ README задачи
→ кнопка «Назад» в браузере
```

Навигация объясняется на трёх уровнях:

1. Корневой README показывает три шага: выбрать направление или собеседование, открыть подборку, после задачи вернуться кнопкой браузера.
2. README каждой подборки одной строкой напоминает: после задачи нажать «Назад», чтобы вернуться к тому же списку.
3. Каждая карточка:
   - сверху содержит компактную ссылку `← Все подборки`;
   - снизу содержит инструкцию `Нажмите «Назад», чтобы вернуться в выбранную подборку`;
   - рядом даёт запасную ссылку `Потерялись? Открыть все подборки`.

Статический Markdown не знает, из какой подборки пришёл ученик. Поэтому кнопка браузера возвращает в точный контекст, а ссылка на корневой README служит гарантированным запасным выходом.

Точные относительные пути:

- из `tasks/<slug>/README.md` на главную — `../../README.md`;
- из любого thematic или interview README на задачу — `../../../tasks/<slug>/README.md`.

## 6. Корневой README

Корневой README содержит только четыре ученических блока:

1. `Как пользоваться базой`.
2. `Подборки по направлениям`.
3. `Симуляции собеседований`.
4. `Где писать код`.

В нём не должно быть:

- таблиц со всеми задачами;
- описания метаданных как источника истины;
- правил работы ИИ-агента;
- Beads, GRACE и knowledge graph terminology;
- maintenance flow;
- технического контракта синхронизации.

Под каждой технологией перечисляются ссылки на конкретные collection README. Рядом с собеседованием показываются только количество задач и примерное общее время.

## 7. Тематические подборки

Каждая тематическая подборка содержит:

- понятное название;
- два-три предложения о том, что тренирует подборка;
- напоминание о возврате кнопкой браузера;
- упорядоченный список задач от более простой к более сложной.

Задача отображается без таблицы:

```md
1. [Порядок выполнения кода](../../../tasks/browser-event-loop-order/README.md)
   Разберитесь, как выполняются обычный код, Promise и setTimeout. Примерно 12 минут.
```

Строка содержит только:

- название и относительную ссылку;
- одно простое предложение;
- примерное время.

Технология понятна из раздела и пути подборки. Формат, сложность и служебные поля в collection README не повторяются.

## 9. Собеседовательные подборки

Каждое собеседование начинается одной инструкцией:

> Запускайте отдельный таймер перед каждой задачей. Указанное время приблизительное: оно помогает держать темп, но не является строгим лимитом. Сначала решайте без подсказок.

Порядок ссылок является рекомендуемым порядком решения. Дополнительные фазы, отчёты и grading rubric не создаются.

## 10. Карта онлайн-редакторов

Редактор определяется не одним полем `Технология`, а требуемым профилем
выполнения. Это сохраняет browser, ESM, DOM и React semantics существующих задач
и не заставляет запускать browser-код в console-only среде.

| Профиль выполнения | Редактор | URL |
| --- | --- | --- |
| Console JavaScript без browser API | Programiz JavaScript Online Compiler | `https://www.programiz.com/javascript/online-compiler/` |
| Browser JavaScript, DOM, HTML/CSS или ESM | CodePen | `https://pen.new` |
| Чистый TypeScript | TypeScript Playground | `https://www.typescriptlang.org/play/` |
| React + TypeScript | Vite React TypeScript in StackBlitz | `https://vite.new/react-ts` |

Все четыре ссылки перечисляются на главной. В каждой карточке одна подходящая ссылка находится рядом с инструкцией по переносу кода.

Профили фиксированы для этой миграции:

- Programiz: `immutable-category-totals`, `stable-product-sort`,
  `loop-closure-bindings`;
- CodePen browser ESM: `this-callback-binding`, `stale-search-response`,
  `delegated-dynamic-list`, `idempotent-event-listeners`,
  `accessible-keyboard-tabs`, `modal-focus-lifecycle`;
- CodePen browser classic script: `browser-event-loop-order`;
- CodePen HTML/CSS: `flex-long-text-overflow`,
  `container-responsive-grid`;
- TypeScript Playground: `discriminated-load-state`,
  `typed-object-property`, `response-union-narrowing`,
  `validate-unknown-profile`;
- `vite.new/react-ts`: `react-derived-list`, `react-batched-counter`,
  `react-effect-subscription`, `react-strictmode-cleanup`.

Для `this-callback-binding` CodePen запускается как browser ESM. До изменения
карточки агент обязан доказать, что три наблюдаемые строки и причины привязки
`this` совпадают с исходным Node ESM-контрактом. Если эквивалентность не
подтверждается, миграция останавливается для выбора другого редактора; учебная
цель или ожидаемый результат не переписываются под ограничения редактора.

Карта редакторов, ссылки на главной и ссылки в карточках образуют одну связанную систему. Замена редактора требует одного атомарного изменения:

- обновить карту в правилах проекта;
- обновить корневой README;
- обновить все затронутые карточки;
- проверить новые ссылки;
- доказать отсутствие старых URL.

Частичная замена запрещена.

## 11. Два режима карточки

### 11.1 Обычная code-first задача

Используется по умолчанию:

1. Название.
2. `← Все подборки`.
3. Короткая инструкция с подходящим редактором.
4. `Условие`.
5. Один полный блок, где задание записано комментариями внутри кода.
6. `Готово, когда`.
7. Инструкция по работе с подсказками.
8. Три закрытые подсказки.
9. Закрытое `Решение`.
10. Закрытая `Самопроверка`.
11. Необязательное `Почитать по теме`.
12. Закрытое `О задаче`.
13. Инструкция возврата.

Первый видимый абзац `Условия` сохраняет существующую учебную цель в
ученической формулировке. Отдельный служебный заголовок `Учебная цель` не
обязателен, но сама цель не удаляется и не подменяется новой.

### 11.2 Комплексная задача

Используется, когда одного комментария недостаточно для контекста:

1. Название.
2. `← Все подборки`.
3. Короткое текстовое `Условие`.
4. Инструкция с редактором.
5. `Код — вставьте его в редактор`.
6. Один или несколько полных блоков.
7. Остальная структура обычной карточки.

Комплексный режим не разрешает возвращать старые секции `Входы`, `Выходы`, `Ограничения и побочные эффекты`, `Примеры` и `Стартовый код` как обязательный boilerplate. Нужная информация пишется коротко в условии, комментариях и `Готово, когда`.

## 12. Контракт копируемого кода

### 12.1 Основное правило

По умолчанию весь стартовый код находится в одном полном блоке. Ученик может скопировать блок целиком и выполнить указанную инструкцию без поиска других файлов.

### 12.2 Несколько файлов

Несколько блоков разрешены только когда задача действительно требует нескольких файлов. Каждый блок:

- содержит полный файл;
- не использует пропуски;
- не говорит `остальной код без изменений`;
- начинается с пути внутри комментария соответствующего языка.

```tsx
// FILE: src/App.tsx

import { useState } from 'react';
```

```css
/* FILE: src/styles.css */

.container {
  display: grid;
}
```

```html
<!-- FILE: index.html -->

<div id="app"></div>
```

Если блок единственный и отдельный файл не нужно создавать или заменять, `FILE:` можно не указывать. При нескольких блоках `FILE:` обязателен в каждом.

Стартовый код и решение используют одинаковое разбиение по файлам.

### 12.3 Контракт по редакторам

- Programiz: один JavaScript-блок для `main.js`; browser API, DOM и
  Node-specific semantics в этом профиле запрещены.
- TypeScript Playground: один TypeScript-блок, если задача не требует нескольких файлов.
- CodePen: базово один HTML-блок со встроенными `<style>` и `<script>`;
  инструкция явно фиксирует classic script или `type="module"`; другое
  разбиение допускается только после ручной проверки точной инструкции.
- `vite.new/react-ts`: базово полная замена `src/App.tsx`; дополнительные файлы разрешены только при реальной учебной необходимости.

## 13. Работа с assets

Текущие `assets/fixture.html` являются текстовым учебным контекстом, а не самостоятельными медиа. Во время миграции их содержимое переносится в карточку и проверяется в выбранном редакторе. После этого старый файл и ссылка удаляются атомарно.

Отдельный `assets/` разрешён только для:

- изображений;
- шрифтов;
- аудио или видео;
- иных бинарных материалов, которые невозможно разумно встроить.

Текстовый код, HTML-разметка, тестовые данные и проверочный сценарий не выносятся в `assets/`.

## 14. Progressive disclosure

### 14.1 Подсказки

Перед подсказками каждая карточка объясняет:

> Застряли? Открывайте подсказки по одной. После каждой закройте подсказку и попробуйте решить задачу снова. Третья подсказка почти подводит к решению, но не показывает готовый код.

Карточка содержит ровно три независимых закрытых блока:

1. `Подсказка 1 — куда смотреть`: понятие или часть кода, на которую нужно обратить внимание.
2. `Подсказка 2 — с чего начать`: конкретный следующий шаг.
3. `Подсказка 3 — почти решение`: алгоритм, псевдокод или ключевая конструкция без готового полного ответа.

Три перефразирования одной мысли не проходят editorial gate. Если три содержательные ступени невозможно сформулировать, карточка переписывается, а не заполняется искусственно.

### 14.2 Решение

`Решение` закрыто по умолчанию и содержит:

1. один или несколько полных блоков согласно стартовому разбиению;
2. короткое `Почему это работает`;
3. необязательный `Другой вариант`, только когда он помогает учебной цели.

`Подход`, `Сложность`, `Компромиссы и альтернативы` больше не являются обязательными секциями. Временная и пространственная сложность добавляются только когда они входят в учебную цель.

### 14.3 Самопроверка

`Самопроверка` — один закрытый блок после решения. Он содержит только вопросы для размышления, без вложенных ответов. Объяснение уже находится в решении.

### 14.4 Теория и дополнительные материалы

Обязательный блок `Теория` удаляется. Контекст распределяется между условием, комментариями, подсказками и объяснением решения.

Необязательное закрытое `Почитать по теме` добавляется только когда целевая ссылка даёт дополнительную учебную ценность. Карточка остаётся самодостаточной без этой ссылки.

## 15. Компактные метаданные

В конце карточки находится один закрытый блок:

```md
<details>
<summary>О задаче</summary>

- Технология: JavaScript
- Подборка: Event loop и асинхронность
- Формат: Предсказать результат
- Сложность: Средняя
- Примерное время: 12 минут

</details>
```

Точные названия полей:

- `Технология`;
- `Подборка`;
- `Формат`;
- `Сложность`;
- `Примерное время`.

Допустимые значения `Технология`:

- `JavaScript`;
- `TypeScript`;
- `HTML/CSS`;
- `HTML/JavaScript`;
- `HTML/CSS/JavaScript`;
- `React/TypeScript`.

`Технология` описывает предмет карточки, но не заменяет профиль выполнения.
Точная связь task slug с редактором задана в разделе 10.

Допустимые значения `Формат`:

- `Написать код`;
- `Исправить код`;
- `Разобрать код`;
- `Предсказать результат`.

Допустимые значения `Сложность`:

- `Базовая`;
- `Средняя`;
- `Продвинутая`.

`Примерное время` записывается как целое число минут: например, `12 минут`. То же число используется в thematic и interview README; слово `примерно` добавляется только в ученическую фразу collection-файла.

Миграция существующих значений детерминирована:

- `Реализация` → `Написать код`;
- `Отладка` → `Исправить код`;
- `Разбор` → `Разобрать код`;
- `Прогноз вывода` → `Предсказать результат`;
- `Базовый` → `Базовая`;
- `Средний` → `Средняя`;
- `Продвинутый` → `Продвинутая`;
- числовая оценка времени сохраняется без изменения.

Изменение формата, сложности или числа минут сверх этой таблицы считается
изменением учебного контракта и требует отдельного решения ментора.

Удаляются поля:

- `Навыки`;
- `Предварительные знания`;
- `Среда выполнения`.

Удаление поля не означает удаление значимой информации:

- наблюдаемые навыки переходят в `Готово, когда`, подсказки или вопросы
  самопроверки;
- prerequisite, отличный от `Нет`, кратко объясняется в видимом условии либо
  рядом с первым местом применения;
- версия, browser/ESM mode и другие runtime assumptions пишутся рядом с кодом,
  когда влияют на решение или ожидаемый результат.

Для каждой карточки migration evidence содержит preservation ledger:
`исходная учебная цель / prerequisite / runtime assumption → новое место`.
Допустимо отметить `not applicable` только с конкретным объяснением, почему
исходное поле не влияло на попытку, решение или проверку. Названия внутренних
проверочных механизмов ученику не показываются.

## 16. Ученический словарь

Основные разрешённые заголовки:

- `Условие`;
- `Код — вставьте его в редактор`;
- `Готово, когда`;
- `Подсказка 1 — куда смотреть`;
- `Подсказка 2 — с чего начать`;
- `Подсказка 3 — почти решение`;
- `Решение`;
- `Почему это работает`;
- `Другой вариант`;
- `Самопроверка`;
- `Почитать по теме`;
- `О задаче`.

В ученическом тексте не используются как структурные заголовки, шаблонные подписи или объяснение устройства карточки:

- `Фикстуры`;
- `Локальный fixture`;
- `Полный входной код`;
- `Входы`;
- `Выходы`;
- `Ограничения и побочные эффекты`;
- `Критерии готовности`;
- `task contract`;
- `metadata`;
- `canonical`;
- `projection`;
- `evidence`.

Слова из этого списка разрешены внутри кода, цитируемого API или предметного объяснения, когда без них меняется технический смысл. Технические термины, являющиеся предметом задачи (`Promise`, `event loop`, `effect`, `cleanup`, `type guard`), сохраняются и объясняются в учебном контексте.

## 17. Источники истины и синхронизация

### 17.1 Источники

- Заголовок карточки — ученическое название задачи.
- `О задаче` — технология, тематическая подборка, формат, сложность и время.
- Тематический README — порядок задач и краткие описания.
- README собеседования — состав и порядок конкретного набора.
- Корневой README — список collection pages и карта редакторов.
- Правила проекта — допустимая структура карточки и атомарные update rules.

### 17.2 Изменение задачи

Одно изменение синхронизирует:

```text
tasks/<slug>/README.md
→ ровно один тематический README
→ ноль или один interview README
→ docs/knowledge-graph.xml
→ docs/verification-plan.xml
→ Beads evidence
```

Время в карточке, тематической подборке и собеседовании совпадает. Редактор
определяется task profile из раздела 10 и совпадает с корневой картой.

### 17.3 Изменение редактора

Агент сначала находит:

- корневую ссылку;
- все карточки соответствующего editor profile;
- правила авторинга и verification expectations.

Затем обновляет их атомарно, проверяет новый URL и доказывает отсутствие старого.

### 17.4 GRACE delta

Во время реализации:

- `docs/requirements.xml` обновляет student journeys, use cases и критерии понятности;
- `docs/technology.xml` фиксирует Markdown-only content contract и карту редакторов;
- `docs/development-plan.xml` обновляет module contracts, data flows, phases и gates;
- `M-CATALOG` расширяет scope с одной таблицы до корневого student hub и `collections/**`;
- `M-TASK-TEMPLATE` получает два режима карточки и новый metadata contract;
- `M-TASK-LIBRARY` получает copy-ready, hints, assets и navigation contracts;
- `M-TASK-VALIDATION` получает новые structural, editorial и synchronization gates;
- `DF-STUDY-TASK`, `DF-ADD-TASK` и `DF-UPDATE-TASK` обновляются под collection-first flow;
- `docs/verification-plan.xml` получает structural, synchronization, content, runtime и rendered gates;
- `docs/knowledge-graph.xml` получает collection paths и обновлённые module annotations;
- `docs/operational-packets.xml` проверяется на старые catalog/card labels и обновляется там, где packet contracts от них зависят;
- `AGENTS.md`, `templates/task-template.md` и `docs/task-validation-policy.md` синхронизируются с новым authoring flow.

Новый GRACE module не требуется: существующие module IDs сохраняются, их контракты уточняются.

Исторические completed phases не переписываются в pending. План реализации
добавляет redesign phases и gates с новыми последовательными ID. Будущие
контракты не помечаются implemented заранее: graph, verification и module
annotations обновляются в той же волне, где соответствующий student-facing
контракт становится фактом.

## 18. Миграционная стратегия

Цель — полная миграция без смешанного финального состояния. Реализация идёт
проверяемыми волнами:

1. новый task contract, authoring rules, editor-profile proof и GRACE planning delta;
2. заполненные collection pages без переключения корневого README;
3. JavaScript-карточки;
4. TypeScript-карточки;
5. HTML/CSS и accessibility-карточки;
6. React-карточки;
7. interview composition, полная синхронизация и атомарное переключение корневого README;
8. финальный rendered audit.

До финального gate допустимы промежуточные технические коммиты, но пользовательский результат считается готовым только когда все 20 карточек, 13 collection pages и корневой README соответствуют новому контракту.

Волны выполняются последовательно: `README.md`, collection files и GRACE shared artifacts являются общими write surfaces. Параллельная подготовка отдельных карточек допустима только до интеграции и не разрешает конкурентные изменения общих файлов.

Старый корневой каталог остаётся рабочим до волны 7. Новый root hub не ссылается
на пустую или частично подготовленную collection. Ветка может содержать
неподключённые collection pages во время миграции, но каждый опубликованный
commit сохраняет рабочий путь от текущего корневого README ко всем доступным
задачам.

### 18.1 Beads decomposition contract

Каждая волна становится одной дочерней Beads-задачей. ID создаются планом
реализации; спецификация фиксирует границы, зависимости и сигнал закрытия:

| Unit | Scope | Depends on | Completion evidence |
| --- | --- | --- | --- |
| `R1` | Task contract, authoring rules, editor-profile proof, pending GRACE redesign phases | Письменное одобрение этой спецификации | Четыре editor URL открываются; все 20 slugs имеют профиль; template/policy/GRACE plan согласованы |
| `R2` | Десять thematic pages с финальным содержанием и три неподключённых interview shells, без root cutover | `R1` | Exact path set; thematic task links, titles, descriptions and times pass; interview pages содержат только общий контракт до `R7` |
| `R3` | Восемь JavaScript/DOM-карточек и удаление текстового asset `stale-search-response` | `R2` | Per-card structure, copy/run, content and target-editor evidence pass before asset deletion |
| `R4` | Четыре TypeScript-карточки | `R3` | Per-card structure, type-check/run and target-editor evidence pass |
| `R5` | Четыре HTML/CSS/accessibility-карточки и удаление двух текстовых assets | `R4` | CodePen/browser/manual visual evidence pass before asset deletion |
| `R6` | Четыре React-карточки | `R5` | `vite.new/react-ts` copy/run and browser evidence pass |
| `R7` | Interview links, graph/verification sync and root cutover | `R6` | All 13 collections, all 20 cards, all duplicated fields and root negative checks pass atomically |
| `R8` | Published GitHub rendered audit and final handoff | `R7` | Full URL inventory plus deep rendered-flow matrix pass; user-acceptance request recorded |

Каждый unit имеет один primary scope, закрывается только по указанному evidence и
трассируется к разделам 3, 8–19 и 22. Фактические `bd` issues не создаются до
письменного одобрения спецификации и отдельного implementation plan.

## 19. Проверка

### 19.1 Структурная

- существует ровно утверждённый set из 10 thematic и 3 interview README без дополнительных collection paths;
- корневой README ссылается на все 13;
- корневой README содержит ровно четыре блока из раздела 6 и не содержит старых task tables, agent-maintenance prose или Beads/GRACE terminology;
- все относительные task links разрешаются;
- каждая карточка встречается ровно в одной thematic collection;
- interview collections содержат ровно 15 уникальных task slugs;
- ни одна задача не встречается в двух interviews;
- task directory set равен утверждённым 20 slugs: ни один не потерян и новый не добавлен;
- каждый interview entry показывает linked student title и exact time, а не slug как ученическое название;
- закрытые blocks имеют парные `<details>` и `</details>`;
- каждая карточка содержит три exact hint summaries;
- `Решение`, `Самопроверка` и `О задаче` закрыты;
- metadata содержит ровно пять требуемых полей;
- code fences сбалансированы;
- при нескольких стартовых блоках каждый содержит `FILE:`;
- старые student-facing labels отсутствуют как headings и template boilerplate.

### 19.2 Синхронизация

- title и time совпадают между карточкой и collections;
- thematic metadata указывает на единственную фактическую collection;
- editor link соответствует task profile из раздела 10;
- корневая editor map и карточки используют одни URL;
- старые editor URL отсутствуют после замены;
- format, difficulty и time преобразованы только по таблице раздела 15;
- каждая исходная учебная цель, prerequisite и значимая runtime assumption
  имеют новое место либо обоснованный `not applicable` в preservation ledger;
- graph annotations и verification refs соответствуют всем task paths и collection paths.

### 19.3 Содержательная

Для каждой карточки проверяются:

- условие понятно без внешнего файла;
- код копируется полностью;
- инструкция редактора воспроизводима;
- `Готово, когда` наблюдаемо;
- три подсказки образуют реальную прогрессию;
- решение полностью удовлетворяет условию;
- `Почему это работает` объясняет ключевую концепцию;
- вопросы самопроверки соответствуют учебной цели;
- служебный жаргон не попал в ученический текст.

### 19.4 Исполняемая и браузерная

- каждая из 20 карточек получает отдельную строку evidence: slug, профиль,
  target editor, инструкция, expected, actual и verdict;
- временный harness разрешён только для предварительной диагностики и не
  заменяет финальный PASS в заявленном онлайн-редакторе;
- JavaScript и TypeScript сверяются в заявленном онлайн-редакторе;
- React и DOM проходят минимальный browser scenario;
- HTML/CSS/JS блоки вручную проверяются в CodePen;
- React-инструкции вручную проверяются в `vite.new/react-ts`;
- CSS и визуальное поведение проверяются вручную, не unit-тестами;
- текстовый asset удаляется только после PASS встроенного replacement;
- внешний материал или editor URL должен открываться без закрытого обязательного доступа.

### 19.5 Rendered GitHub flow

Проверяется опубликованная ветка или PR:

```text
README
→ одна collection каждого технологического раздела
→ одна задача каждого карточного режима
→ три подсказки по одной
→ решение
→ самопроверка
→ возврат
```

URL inventory открывает root README, все 13 collection pages и все 20 task
pages. Для каждой страницы фиксируются resolved URL, видимый title, отсутствие
404 и корректность обязательных links/details.

Глубокий flow выполняется минимум для одной collection каждого технологического
раздела, всех трёх interviews, одной задачи каждого карточного режима, каждого
editor profile и всех карточек, ранее зависевших от `assets/fixture.html`.

## 20. Stop conditions

Миграция карточки останавливается, если:

- невозможно создать три разные полезные подсказки;
- код нельзя скопировать и запустить по инструкции;
- для решения нужен неописанный файл;
- технология или редактор неоднозначны;
- task profile отсутствует в разделе 10 или не воспроизводит исходную среду;
- несколько блоков созданы без реальной необходимости;
- `FILE:` path не соответствует инструкции;
- встроенный replacement не воспроизводит поведение удаляемого asset;
- metadata и collection расходятся;
- одна задача попала в несколько thematic или interview collections;
- обязательная ссылка не открывается;
- GitHub неожиданно отображает `<details>`, code fences или relative links.

Нельзя выдавать непроверенную карточку за PASS, заполнять три подсказки повторениями или сохранять скрытый контекст ради завершения волны.

## 21. Риски и меры

| Риск | Мера |
| --- | --- |
| Упрощение удалит важные ограничения | Сохранить их коротко в условии, comments и `Готово, когда`; пройти content review |
| Три подсказки станут формальными | Проверять различие направления, первого шага и почти-алгоритма |
| CodePen/StackBlitz потребуют иной структуры | Ручной copy/run PASS до удаления assets |
| Редактор изменит browser, ESM или Node semantics | Фиксированный task profile, equivalence proof и stop без переписывания ожидаемого результата |
| Collection data разойдутся | Exact uniqueness, title, time и link checks |
| Корневой README снова разрастётся | На главной только ссылки на collections, editors и три шага |
| React смешается с общим JavaScript | Отдельный React namespace и ровно одна thematic membership |
| Editor link поменяется частично | Atomic replacement и forbidden-old-URL scan |
| Будущий docs generator потребует миграции | Стабильные Markdown paths, полные страницы и отсутствие GitHub-only hidden context |

## 22. Критерии завершения

- все 20 существующих задач мигрированы;
- каждая карточка соответствует одному из двух режимов;
- все карточки self-contained;
- три подсказки, решение, самопроверка и metadata соответствуют контракту;
- текстовые `assets/fixture.html` встроены и удалены;
- корневой README является коротким student hub;
- существуют и проходят проверку 10 thematic collections;
- существуют и проходят проверку 3 interviews по 5 уникальных задач;
- тематические и interview duplicates отсутствуют по утверждённым правилам;
- editor map, task profiles и все карточки синхронизированы;
- ученический словарь не содержит запрещённого служебного жаргона;
- GRACE shared artifacts отражают новую фактическую архитектуру;
- Markdown, XML, links, whitespace и rendered GitHub gates проходят;
- Docusaurus и deployment не были добавлены;
- пользователь отдельно принимает полностью мигрированную библиотеку после финального review.
