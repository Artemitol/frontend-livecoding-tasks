# Дизайн базы frontend live-coding задач

Дата: 2026-07-22
Статус: дизайн одобрен в диалоге; письменная спецификация ожидает финального review

## 1. Цель

Создать GitHub-first базу знаний с качественными frontend live-coding задачами. Ученик должен уметь выбрать упражнение по теме, формату, сложности и времени, понять контракт без скрытого внешнего контекста, открыть теорию или подсказку по необходимости и сверить своё решение после попытки.

Первоначальная библиотека включает все самостоятельно сформулированные кандидаты, которые прошли строгую проверку. Заранее заданного количества нет: семантические дубли объединяются, некорректные или педагогически слабые кандидаты не публикуются.

## 2. Подтверждённые решения

- Основной интерфейс ученика — rendered view репозитория на GitHub.
- Основной артефакт — Markdown; обязательный runtime не нужен.
- Каждая задача хранится в `tasks/<stable-slug>/README.md`.
- Корневой `README.md` содержит тематические таблицы; каждая задача встречается ровно один раз.
- Метаданные карточки являются источником истины для каталога и knowledge graph.
- Задачи формулируются самостоятельно; неоригинальные формулировки и код не принимаются.
- Семантически одинаковые кандидаты объединяются в одну улучшенную карточку.
- Порог валидации строгий; только статус `accepted` разрешает публикацию.
- Работа идёт волнами по 8–10 принятых задач; последняя неполная волна может содержать 1–7.
- Агент предоставляет отчёт волны, а ментор принимает волну целиком с выборочной проверкой.
- Теория, каждая подсказка и решение находятся в независимых закрытых `<details>`.
- Официальная документация, статьи и видео допустимы как целевые учебные ссылки, но не заменяют локальные условие, fixtures или решение.
- Изменения выполняются в отдельном worktree и ветке `feature/<beads-story-id>` от актуального `origin/main`.

## 3. Пользователи и сценарии

### Ученик

- Выбирает задачу по технологии, теме, формату, уровню, времени, навыкам и предварительным знаниям.
- Видит учебную цель, однозначное условие и критерии готовности без раскрытия спойлеров.
- По необходимости открывает теорию, дополнительные материалы и подсказки по одной.
- После собственной попытки открывает решение и проходит самопроверку.

### Ментор

- Определяет спорные границы содержания и controlled vocabulary.
- Получает отчёт по каждой волне с evidence и оставшимися рисками.
- Принимает волну целиком и при необходимости выборочно проверяет карточки.

### ИИ-агент

- Самостоятельно формулирует кандидатов и проверяет их на дубли.
- Применяет единый task contract и строгий validation flow.
- Не публикует `needs-rewrite`, `rejected` или `duplicate`.
- Атомарно синхронизирует карточку, каталог, knowledge graph и Beads evidence.
- Останавливается при неоднозначном контракте или недоступном обязательном evidence.

## 4. Не-цели

- Исполняемая образовательная платформа.
- Обязательный package manager, task runner или локальная установка для чтения базы.
- Генератор каталога или CI-пайплайн в первой версии.
- Публикация черновиков и карантинных карточек рядом с принятыми задачами.
- Защита решения от намеренного просмотра raw Markdown.
- Переписывание полной документации библиотек и платформ внутри карточек.

## 5. Архитектура

```text
M-GOVERNANCE
→ M-TASK-TEMPLATE
→ M-TASK-VALIDATION
→ M-TASK-LIBRARY
→ M-CATALOG
```

| ID | Назначение | Целевые артефакты | Verification ref |
| --- | --- | --- | --- |
| `M-GOVERNANCE` | Правила авторинга, worktree, синхронизации и остановки | `AGENTS.md`, `.gitignore`, `docs/*.xml` | `V-M-GOVERNANCE` |
| `M-TASK-TEMPLATE` | Канонический контракт карточки | `templates/task-template.md` | `V-M-TASK-TEMPLATE` |
| `M-TASK-VALIDATION` | Дедупликация и строгий gate до публикации | `docs/task-validation-policy.md`, Beads evidence | `V-M-TASK-VALIDATION` |
| `M-TASK-LIBRARY` | Только принятые карточки и локальные assets | `tasks/<slug>/README.md`, `assets/` | `V-M-TASK-LIBRARY` |
| `M-CATALOG` | Тематическая проекция канонических метаданных | `README.md` | `V-M-CATALOG` |

`M-TASK-VALIDATION` отделяет подготовку кандидата от публикации. Его выходом является `ValidationDecision`; только `accepted` передаёт `AcceptedTaskCard` в библиотеку.

## 6. Контракт карточки

### 6.1 Файловая структура

```text
tasks/
  <stable-slug>/
    README.md
    assets/          # необязательно
```

Slug является стабильным идентификатором. Его изменение — отдельная миграция с полной проверкой входящих ссылок.

### 6.2 Обязательные метаданные

Таблица использует точные названия:

- `Технологии`;
- `Тема`;
- `Формат`;
- `Уровень`;
- `Время`;
- `Навыки`;
- `Предварительные знания`;
- `Среда выполнения`.

Допустимые значения `Формат`: `Реализация`, `Отладка`, `Разбор`, `Прогноз вывода`.

Допустимые значения `Уровень`: `Базовый`, `Средний`, `Продвинутый`. Уровень описывает сложность самой задачи, а не грейд разработчика.

Калибровка уровня:

- `Базовый` — одна основная концепция, прямой контракт и ограниченное число корнер-кейсов;
- `Средний` — сочетание нескольких концепций, значимые ограничения либо необходимость выбрать подход;
- `Продвинутый` — нетривиальная модель выполнения, архитектурные компромиссы, сложное состояние, асинхронность или необходимость аргументировать несколько допустимых решений.

`Среда выполнения` фиксирует значимые версии и режим: например, ECMAScript module, Node.js, браузер, TypeScript 5.x или React 19.

### 6.3 Обязательная структура

1. Название и учебная цель.
2. Таблица метаданных.
3. Закрытый блок `Теория`.
4. Видимый раздел `Условие`.
5. Входы, выходы, ограничения и допустимые побочные эффекты.
6. Стартовый код, когда он нужен.
7. Нормальные примеры и значимые корнер-кейсы с ожидаемым результатом.
8. Видимый раздел `Критерии готовности`.
9. Ноль или несколько независимых блоков `Подсказка N`.
10. Один закрытый блок `Решение` с объяснением, кодом, сложностью и существенными компромиссами.
11. Видимый раздел `Самопроверка`.
12. `Дополнительные материалы`, когда они действительно помогают изучению.

Для `Разбора` и `Прогноза вывода` вместо обычных входов и выходов фиксируются точная среда, режим выполнения и вопросы ученику. Для UI-задач фиксируются состояния, взаимодействия и ручные визуальные критерии.

### 6.4 Внешние материалы

- Официальная документация предпочтительна для API-контрактов и объёмной теории.
- Качественные статьи и видео допустимы по необходимости.
- Карточка кратко объясняет, зачем открывать материал и что именно изучить.
- Обязательное предварительное чтение явно отражается в `Предварительных знаниях`.
- Большие фрагменты документации не копируются.
- Внешний материал не может быть единственным местом, где находятся условие, стартовый код, fixtures или решение.
- Доступность ссылки проверяется при принятии задачи.
- Проверка допускает успешный HTTP-ответ или рабочий redirect на ожидаемый материал; обязательное чтение не должно требовать закрытого аккаунта или платной подписки.

## 7. Строгая валидация

Каждый кандидат проходит gates в указанном порядке:

1. `Identity` — нет принятой задачи с той же учебной целью; близкие варианты объединены.
2. `Learning value` — проверяется конкретный frontend-навык, а не случайный трюк без педагогической ценности.
3. `Contract` — однозначны среда, входы, выходы, ограничения, мутация и ошибки.
4. `Local completeness` — условие, fixtures, стартовый код и решение доступны локально.
5. `Examples` — happy path, граница и ошибка либо пустой результат непротиворечивы, когда применимы.
6. `Solution` — решение удовлетворяет контракту; сложность и компромиссы описаны честно.
7. `Verification` — получено evidence подходящего типа.
8. `Editorial` — терминология, Markdown и формулировки соответствуют проектному контракту.

### 7.1 Реестр кандидатов

Перед аудитом агент замораживает конечный нейтральный реестр кандидатов в Beads. Каждая запись имеет стабильный candidate ID, самостоятельно сформулированную учебную цель, предполагаемую тему и ссылку на story. Реестр не содержит внешнего происхождения или заимствованных формулировок.

Для каждого candidate ID фиксируются решение валидации, причина, тип evidence, наблюдаемый результат, duplicate target при объединении, wave ID для `accepted` и оставшийся риск. Story может завершиться только когда число terminal decisions совпадает с размером замороженного реестра и `needs-rewrite` не осталось.

Новый кандидат после freeze добавляется явным Beads update с новым ID и увеличивает ожидаемое число terminal decisions; он не может появиться в task wave неучтённо.

### 7.2 Результаты

- `accepted` — можно атомарно публиковать.
- `needs-rewrite` — кандидат можно исправить, но публикация запрещена.
- `rejected` — кандидат некорректен или не имеет достаточной учебной ценности.
- `duplicate` — полезные различия объединяются с основной задачей.

Черновой пул и отклонённые карточки не хранятся в `tasks/`. Нейтральный статус и причина остаются в Beads.

### 7.3 Гибридное evidence

- JavaScript выполняется во временном harness в заявленной среде.
- TypeScript дополнительно проходит временную проверку типов.
- React и DOM проверяются минимальным временным примером либо браузерным сценарием.
- UI проверяется вручную в браузере; CSS и визуальное оформление не утверждаются unit-тестами.
- `Разбор` и `Прогноз вывода` получают пошаговый trace и фактическую сверку в заявленной среде.
- Структура Markdown, закрытые `<details>`, локальные ссылки и catalog projection проверяются детерминированно.

Временные harness-файлы не становятся постоянным runtime репозитория.

## 8. Каталог

Корневой `README.md` содержит тематические разделы с таблицами. Одна строка отображает:

- название и относительную ссылку;
- технологии;
- формат;
- уровень;
- время;
- навыки;
- предварительные знания.

Каждая карточка принадлежит ровно одной основной теме. Пересекающиеся навыки остаются метаданными и не создают повторных строк. Внутри темы задачи сортируются по уровню, затем по названию.

Тема и другие классификационные значения берутся из controlled vocabulary. Новое или неоднозначное значение требует решения ментора. Метаданные карточки каноничны; каталог не может молча изменить их.

## 9. Потоки данных

### `DF-VALIDATE-TASK`

```text
тема-кандидат
→ дедупликация
→ самостоятельная формулировка
→ task contract
→ semantic review
→ hybrid evidence
→ ValidationDecision
```

### `DF-PUBLISH-TASK-WAVE`

```text
8–10 accepted cards; последняя волна может содержать 1–7
→ tasks/ и assets
→ тематический каталог
→ knowledge-graph annotations
→ structural and projection checks
→ commit и push проверенной ветки
→ отчёт волны
→ пользовательское принятие либо follow-up fix commit
→ закрытие дочерней Beads-задачи
```

### `DF-STUDY-TASK`

```text
тематический каталог
→ карточка
→ видимые условие и критерии
→ опциональная теория и материалы
→ подсказки по одной
→ решение после попытки
→ самопроверка
```

### `DF-UPDATE-TASK`

```text
изменение карточки
→ поиск производных артефактов и входящих ссылок
→ повторная валидация затронутого контракта
→ синхронизация catalog и graph
→ projection and link checks
```

## 10. Ошибки и stop conditions

- Неоднозначная среда или ожидаемый результат → `needs-rewrite`; агент не угадывает.
- Противоречивые примеры или решение только для happy path → публикация запрещена.
- Технически некорректная или педагогически слабая тема → `rejected`.
- Дубликат → `duplicate` с переносом полезных деталей в основную карточку.
- Несколько корректных решений → одно основное решение и краткое сравнение альтернатив.
- Нестабильные сеть, время или внешнее состояние → локальная fixture, fake clock либо детерминированный adapter.
- Недоступное browser-only evidence → `BLOCKED`, не `PASS`.
- Сломанный дополнительный материал → заменить или удалить до принятия волны.
- Unexpected GitHub rendering → остановить принятие до ручной проверки.
- Drift карточки, каталога и graph → атомарная операция незавершена.

## 11. Git и worktree

1. Определить, не является ли текущий checkout уже linked worktree.
2. Выполнить `git fetch origin`.
3. Использовать актуальный `origin/main`, а не предположительно свежий локальный `main`.
4. Предпочесть native worktree facility; иначе использовать `git worktree add`.
5. Для story создать или переиспользовать `feature/<story-id>` и одну рабочую директорию для всех дочерних issues.
6. Для локального worktree предпочесть игнорируемую `.worktrees/`.
7. До изменений получить чистый project-appropriate baseline.
8. После технически прошедшей волны создать focused Conventional Commit и push активной ветки, затем предоставить отчёт ментору.
9. Если ментор просит изменения, внести их в той же ветке, повторить gates и добавить follow-up commit; Beads issue остаётся открытым до принятия.
10. Перед финальной передачей повторно fetch `origin` и проверить divergence.
11. Не выполнять force-push, переписывание опубликованной истории или конфликтную интеграцию main без отдельного полномочия.

## 12. Порядок реализации

### Phase 1 — Governance

Синхронизировать `AGENTS.md`, `.gitignore`, GRACE-артефакты и worktree-контракт.

### Phase 2 — Task contract and validation

Создать `templates/task-template.md` и `docs/task-validation-policy.md`; проверить metadata schema, progressive disclosure и validation outcomes.

### Phase 3 — Student entry point

Создать корневой `README.md` с тематической навигацией и явным пустым состоянием.

### Phase 4 — Candidate audit

Заморозить нейтральный реестр кандидатов в Beads, затем дедуплицировать их и зафиксировать validation decisions.

### Phase 5 — Task waves

Готовить и принимать задачи волнами по 8–10; последняя неполная волна может быть меньше. Каждая волна атомарно меняет карточки, каталог, graph и evidence.

### Phase 6 — Final audit

Проверить, что все кандидаты имеют terminal status, все принятые карточки представлены ровно один раз, ссылки работают, controlled vocabulary последователен, GRACE XML валиден и пользователь принял каждую волну.

### Phase 7 — Scale review

Рассматривать генератор, валидатор или CI только после наблюдаемого drift либо доказанной чрезмерной стоимости ручной проверки.

## 13. Критерии завершения истории

- Число terminal decisions совпадает с размером замороженного candidate register; каждый кандидат имеет `accepted`, `rejected` или `duplicate`, а `needs-rewrite` отсутствуют.
- Все дубли объединены.
- В `tasks/` находятся только строго принятые карточки.
- Каждая карточка соответствует шаблону и имеет подходящее evidence.
- Каждая задача встречается ровно один раз в каталоге и graph annotations.
- Обязательные локальные и дополнительные внешние ссылки проверены.
- Все волны приняты ментором.
- Все GRACE, Markdown, whitespace и Git gates проходят.
- Ветка опубликована без force-push.

## 14. Риски и меры

| Риск | Мера |
| --- | --- |
| Технически неверное решение | Строгий `Solution` gate и исполняемое либо trace evidence |
| Семантические дубли | `Identity` gate до авторинга карточки |
| Catalog drift | Атомарная task/catalog/graph операция и full projection check |
| Случайные спойлеры | Независимые закрытые `<details>` |
| Broken links | Проверка локальных и внешних ссылок при принятии волны |
| Нестабильное внешнее окружение | Локальные fixtures и детерминированные adapters |
| Разрастание теории | Краткий контекст и целевые ссылки на документацию |
| Несопоставимые browser результаты | Точная `Среда выполнения`; недоступное evidence означает `BLOCKED` |
| Долгая история отстаёт от main | Повторный fetch и divergence review перед финальной передачей |

## 15. Критерии готовности дизайна

- Пять модулей имеют однозначные границы и verification refs.
- Task contract задаёт точные metadata labels, форматы, уровни и среду.
- Validation outcomes не позволяют черновику попасть в библиотеку.
- Гибридная проверка отделена от постоянного runtime репозитория.
- Каталог масштабируется тематическими таблицами без дублей.
- Внешние материалы разрешены без потери локального контракта задачи.
- Worktree и ветка создаются от актуального `origin/main`.
- Stop conditions запрещают выдавать недоступное evidence за PASS.
