# Дизайн GitHub-базы frontend live-coding задач

Дата: 2026-07-22
Статус: дизайн одобрен в диалоге; письменная спецификация ожидает финального review

## 1. Цель

Создать репозиторий-базу знаний с самодостаточными frontend-задачами на JavaScript, TypeScript и React. Ментор пополняет базу через ИИ-агента, а основной пользователь — ученик, который открывает задачи напрямую на GitHub и тренируется самостоятельно.

Главный пользовательский результат: ученик может выбрать подходящую задачу, понять условие без внешнего контекста, при необходимости дочитать теорию, открыть ровно одну подсказку и только после собственной попытки посмотреть решение.

## 2. Подтверждённые решения

- Основной интерфейс ученика — rendered view репозитория на GitHub.
- Основной артефакт — Markdown; запуск репозитория не требуется.
- Каждая задача хранится в `tasks/<task-slug>/README.md`.
- Дополнительные изображения и статические материалы хранятся рядом в `tasks/<task-slug>/assets/` только при необходимости.
- Корневой `README.md` служит каталогом задач.
- Источник истины для каталога — метаданные внутри карточек задач.
- Каталог синхронизирует ИИ-агент по строгому контракту; генератор и обязательный runtime не добавляются.
- Теория, каждая подсказка и решение находятся в независимых `<details>` без атрибута `open`.
- Новое или существенно изменённое решение проходит содержательный review ментора.
- Slug задачи является стабильным идентификатором; его изменение оформляется как отдельная миграция ссылок.
- Review и completion evidence хранятся в Beads issue соответствующей task wave.
- Текст и стабильные названия секций задачи по умолчанию русскоязычные; исключение задаёт ментор.

## 3. Пользователи и сценарии

### Ученик

- Выбирает задачу по технологии, теме, уровню, времени, навыкам и prerequisites.
- Читает видимую часть задания и критерии готовности.
- При необходимости раскрывает теорию.
- Раскрывает подсказки по одной, не видя остальные.
- После попытки раскрывает решение и выполняет самопроверку.

### Ментор

- Формулирует запрос на новую задачу или изменение существующей.
- Принимает решения в неоднозначных случаях классификации или содержания.
- Проверяет техническую и педагогическую корректность решения.

### ИИ-агент

- Читает GRACE-контракты и канонический шаблон.
- Создаёт или изменяет карточку задачи.
- Атомарно синхронизирует каталог, knowledge graph и verification evidence.
- Не угадывает неоднозначные метаданные и не добавляет tooling без нового решения.

## 4. Не-цели

- Исполняемая образовательная платформа.
- Обязательный task runner, package manager или локальная установка.
- Генератор каталога или CI-пайплайн на первом этапе.
- Обязательные runnable-решения и автоматические тесты для каждой задачи.
- Защита решения от намеренного просмотра raw Markdown или поиска GitHub.

`<details>` предотвращает случайные спойлеры, но не является механизмом доступа или шифрования.

## 5. Архитектура модулей

| ID | Название | Тип | Назначение | Зависимости | Целевые пути | Verification ref |
| --- | --- | --- | --- | --- | --- | --- |
| `M-GOVERNANCE` | Project Governance | `UTILITY` | Правила авторинга, синхронизации, проверки и остановки | нет | `AGENTS.md`, `docs/*.xml` | `V-M-GOVERNANCE` |
| `M-TASK-TEMPLATE` | Task Template | `UTILITY` | Каноническая структура самодостаточной карточки | `M-GOVERNANCE` | `templates/task-template.md` | `V-M-TASK-TEMPLATE` |
| `M-TASK-LIBRARY` | Task Library | `DATA_LAYER` | Карточки задач и их канонические метаданные | `M-TASK-TEMPLATE`, `M-GOVERNANCE` | `tasks/<task-slug>/README.md`, `assets/` | `V-M-TASK-LIBRARY` |
| `M-CATALOG` | Student Catalog | `ENTRY_POINT` | Главная точка входа и единая производная таблица метаданных | `M-TASK-LIBRARY`, `M-GOVERNANCE` | `README.md` | `V-M-CATALOG` |

Зависимости образуют однонаправленную цепочку без циклов:

```text
M-GOVERNANCE
→ M-TASK-TEMPLATE
→ M-TASK-LIBRARY
→ M-CATALOG
```

Knowledge graph содержит обратные semantic CrossLinks для навигации, но они не меняют направление implementation dependencies.

`TaskMetadata` принадлежит `M-TASK-TEMPLATE`, потому что шаблон определяет metadata schema до появления библиотеки. `M-TASK-LIBRARY` публикует агрегат `TaskMetadataSet`, который потребляет каталог; скрытого dependency cycle нет.

## 6. Контракт карточки задачи

### Файловая структура

```text
tasks/
  <task-slug>/
    README.md
    assets/          # необязательно
```

### Обязательные метаданные

- Технология.
- Тема.
- Уровень.
- Оценочное время.
- Отрабатываемые навыки.
- Prerequisites, включая относительные ссылки на другие задачи, когда они нужны.

Метаданные в карточке являются каноническими. Каталог не может переопределять или исправлять их молча.

Каноническая таблица использует точные русские названия строк: `Технологии`, `Тема`, `Уровень`, `Время`, `Навыки`, `Предварительные знания`. Эти якоря являются частью машинно-читаемого контракта и не заменяются синонимами.

Агент переиспользует существующие значения технологии, темы и уровня. Новое значение требует решения ментора, чтобы не создавать синонимы. Начальный словарь уровней фиксируется вместе с первой одобренной task wave. Время задаётся в минутах или диапазоном минут.

### Обязательная структура

1. Название и краткая учебная цель.
2. Компактная таблица метаданных.
3. Закрытый блок `<details>` с теорией, достаточной для конкретной задачи.
4. Видимый раздел `Условие`.
5. Стартовый код, когда он нужен для постановки задачи.
6. Видимый раздел `Критерии готовности`.
7. Ноль или несколько независимых блоков `Подсказка N`, каждый в отдельном `<details>`.
8. Один закрытый блок `Решение` с объяснением, кодом и важными компромиссами.
9. Видимый раздел `Самопроверка`.

Теория должна объяснять только знания, необходимые для текущей задачи. Карточка остаётся самодостаточной, но не превращается в общий учебник по теме.

## 7. Каталог и синхронизация

Корневой `README.md` содержит одну компактную каноническую таблицу. Каждая задача представлена ровно одной строкой со всеми обязательными метаданными. Каталог является производным артефактом.

Контракт изменения задачи:

1. Создать или изменить `tasks/<task-slug>/README.md`.
2. Прочитать канонические метаданные карточки.
3. Обновить соответствующее место в корневом каталоге.
4. Обновить `docs/knowledge-graph.xml` и связанные verification facts.
5. Доказать, что задача представлена в каталоге ровно один раз.
6. Разрешить все относительные ссылки на prerequisites и assets.
7. Зафиксировать результат структурной проверки и статус review ментора в Beads issue task wave.

Добавление, удаление, переименование или реклассификация задачи не считается завершённой при частично выполненном контракте.

Каждая принятая карточка добавляет под `M-TASK-LIBRARY` одну публичную аннотацию `export-<task-slug>`. Она даёт агенту точный graph anchor, не превращая каждую карточку в отдельный архитектурный модуль.

## 8. Потоки данных

### `DF-ADD-TASK`

```text
Запрос ментора
→ чтение governance и task template
→ разрешение метаданных
→ создание task card
→ синхронизация catalog
→ синхронизация knowledge graph
→ структурная проверка
→ review решения ментором
```

Агент останавливается до записи при неоднозначной классификации, отсутствующем prerequisite или необходимости нового tooling.

### `DF-STUDY-TASK`

```text
Каталог GitHub
→ выбор по метаданным
→ карточка задачи
→ видимое условие и критерии
→ опциональная теория
→ опциональные подсказки по одной
→ опциональное решение
→ самопроверка
```

### `DF-UPDATE-TASK`

```text
Изменение карточки или метаданных
→ поиск производных артефактов и входящих ссылок
→ обновление карточки
→ синхронизация catalog и graph
→ проверка uniqueness, metadata equality и link resolution
→ verification evidence
```

Смена темы или уровня не меняет slug. Смена slug требует отдельной миграции и полной проверки входящих ссылок.

## 9. Verification surfaces

### `V-M-GOVERNANCE`

- Все `docs/*.xml` проходят `xmllint`.
- Нет незаполненных template placeholders.
- Все `M-*`, `V-M-*`, `UC-*`, `DF-*`, `VF-*` и `Phase-*` ссылки разрешаются.
- Каждая принятая карточка имеет ровно одну `export-<task-slug>` graph annotation.
- Planning artifacts не противоречат друг другу.

### `V-M-TASK-TEMPLATE`

- Присутствуют все обязательные метаданные и разделы.
- Теория, каждая подсказка и решение имеют отдельный `<details>`.
- Ни один из этих блоков не использует `open`.
- Вложенные заголовки и fenced code корректно отображаются на GitHub.
- Rendered-view review обязателен при изменении шаблона или HTML-структуры.

### `V-M-TASK-LIBRARY`

- Карточка соответствует текущему шаблону.
- Задача самодостаточна и содержит достаточные критерии готовности.
- Все prerequisites и assets существуют.
- Version assumptions для JavaScript, TypeScript, React или browser APIs указаны, если влияют на решение.
- Новое или существенно изменённое решение имеет review ментора.

### `V-M-CATALOG`

- Каждая карточка представлена ровно один раз.
- Каждая относительная ссылка разрешается.
- Проецируемые метаданные совпадают с карточкой.
- До появления первой задачи каталог содержит явное пустое состояние.
- Каталог использует одну строку на задачу и все обязательные metadata columns, поэтому uniqueness не конфликтует с несколькими тематическими представлениями.

### Evidence anchors

В Markdown-модулях runtime logs не применяются. Стабильные наблюдаемые якоря:

```text
metadata table
Условие
Критерии готовности
Теория
Подсказка N
Решение
Самопроверка
```

Verification evidence содержит `moduleId`, `verificationRef`, путь артефакта, выполненную проверку, наблюдаемый результат, Beads issue ID и mentor-review status.

## 10. Mental walkthroughs

### Ученик открывает задачу

Каталог показывает достаточно метаданных для выбора. Относительная ссылка открывает карточку в текущей ветке. Условие и критерии видны сразу. Guidance blocks закрыты. Ученик может раскрыть один блок, не раскрывая остальные. Ошибка любого звена наблюдаема как broken link, metadata drift, missing section или unexpected rendering.

### Агент добавляет задачу

Агент сначала читает governance и template, затем разрешает метаданные. После записи карточки он обновляет два производных артефакта и запускает cross-module проверки. Структурный PASS не закрывает содержательный review решения.

### Агент реклассифицирует задачу

Канонические метаданные меняются в карточке. Агент перемещает каталоговую проекцию, не меняя stable slug, и перепроверяет graph facts. Если требуется смена slug, обычный flow останавливается и переключается на migration scope.

## 11. Порядок реализации

### Phase 1 — Governance

Завершить и проверить GRACE planning artifacts. Эта фаза должна закончиться до создания project-facing Markdown modules.

### Phase 2 — Task Contract

Создать `templates/task-template.md` и проверить его GitHub-first progressive-disclosure contract.

### Phase 3 — Student Entry Point

Создать корневой `README.md`, объяснить навигацию и показать явное пустое состояние каталога. `M-CATALOG` принимает пустой `TaskMetadataSet`, поэтому эта фаза не требует преждевременно создавать первую задачу.

### Phase 4 — Task Waves

Добавлять задачи небольшими волнами. Минимальная волна атомарно включает task card, catalog projection, graph delta, verification evidence и mentor-review status в Beads issue.

### Phase 5 — Scale Review

Вернуться к вопросу генератора или валидатора только после появления наблюдаемой проблемы масштаба или drift. Автоматизация требует нового явного решения и отдельного `Gate-Phase-5` с Beads evidence.

## 12. Stop conditions

Агент прекращает автономное выполнение и запрашивает решение, если:

- технология, тема, уровень или prerequisites неоднозначны;
- prerequisite или asset отсутствует;
- карточка, каталог и graph противоречат друг другу;
- GitHub-rendered view отличается от template contract;
- решение требует неописанных знаний или сомнительно по корректности;
- изменение требует нового runtime, generator, CI или site framework;
- попытка обычного обновления фактически меняет stable slug.

## 13. Риски и меры

| Риск | Мера |
| --- | --- |
| Catalog drift | Атомарный agent contract и full projection check после каждой task wave |
| Дробление словаря тем | Контролируемые значения и остановка при неоднозначной классификации |
| Неверное решение | Обязательный mentor content review |
| Сломанное GitHub-отображение | Rendered-view gate при изменении шаблона или HTML |
| Случайный спойлер | Закрытые independent details blocks |
| Намеренный просмотр решения | Принятое ограничение; raw Markdown не защищён |
| Разрастание теории | Теория ограничена знаниями, необходимыми для конкретной задачи |
| Broken links после rename | Stable slug по умолчанию; отдельная migration verification при rename |

## 14. Критерии готовности дизайна

- Все пользовательские сценарии связаны с data flows.
- Каждый модуль имеет purpose, dependencies, target paths и verification ref.
- Для каждого значимого модуля определены success и failure scenarios.
- Порядок реализации соответствует dependency layers.
- Нет обязательной runtime-инфраструктуры.
- Структурная проверка и содержательный mentor review разделены.
- Ограничения GitHub-first progressive disclosure описаны явно.
- Stop conditions не позволяют агенту молча расширить scope.
