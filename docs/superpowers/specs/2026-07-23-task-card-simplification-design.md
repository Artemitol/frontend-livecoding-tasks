# Упрощение карточек и задачи, приближённые к реальной работе

## 1. Статус и решение

Эта спецификация продолжает redesign библиотеки на ветке
`feature/frontend-livecoding-tasks-kln`.

Проверенный commit `7762913bddcdfb5a29e74dd384570dd89af6d672` технически
корректен, но не принят пользователем как финальный student experience.
Карточки остаются перегруженными: отдельные README занимают 109–428 строк,
браузерные задачи дважды содержат полный HTML-документ, а служебная трактовка
учебной цели попала в видимое условие и starter-код.

Решение:

1. Переписать двадцать существующих карточек как короткие сфокусированные
   задания.
2. Ввести отдельный класс и подборку `Приближённые к реальной работе`.
3. Добавить первую задачу этого класса: React-список пользователей на
   DummyJSON с последовательно расширяющимися требованиями.
4. Не считать библиотеку принятой до новой полной миграции, rendered audit и
   явного пользовательского решения.

Beads issue:
`frontend-livecoding-tasks-kln-card-simplification-spec`.

## 2. Цель

Студент открывает карточку и сразу видит:

- что требуется сделать;
- в каком редакторе запускать код;
- минимальный рабочий starter;
- подсказки и решение, скрытые до запроса.

Карточка не объясняет устройство библиотеки, не ведёт пользователя за руку по
навигации и не маскирует маленькое задание под мини-проект из-за boilerplate.

## 3. Не входит в scope

- обязательный package manager или runnable repository;
- отдельное приложение для просмотра задач;
- автоматизированные CSS- или visual-тесты;
- переписывание опубликованной Git-истории;
- автоматическое принятие библиотеки от имени пользователя;
- жёсткий лимит строк, одинаковый для всех типов задач;
- сохранение старого текста только ради формального preservation ledger.

## 4. Два класса задач

### 4.1 Сфокусированная задача

Используется по умолчанию.

Свойства:

- одно центральное действие;
- обычная продолжительность 10–30 минут;
- небольшой starter без инфраструктурной обвязки;
- одно условие без параллельной проверки нескольких смежных умений;
- второстепенные edge cases удаляются, если не определяют суть задания.

Размер кода не является самостоятельным gate. Необычно большой starter
считается editorial-сигналом: автор должен доказать, что в карточке нет второй
задачи, harness или лишнего окружения.

### 4.2 Приближённая к реальной работе

Используется для самостоятельной функциональности или небольшого проекта.

Свойства:

- обычная продолжительность 45–60 минут;
- несколько связанных продуктовых требований допустимы;
- разрешены API, загрузка, ошибки, пустые состояния и несколько компонентов;
- сложность возникает из требуемого поведения, а не из boilerplate;
- этапы расположены от базового результата к расширенному.

Такая задача:

- остаётся в одной основной тематической подборке;
- дополнительно входит в отдельную подборку
  `Приближённые к реальной работе`;
- заранее показывает формат и примерное время в обоих списках.

## 5. StudentTaskCard

### 5.1 Точный порядок

Каждая карточка содержит:

1. Название.
2. Короткую инструкцию с целевым редактором.
3. `Условие`.
4. Starter-код.
5. Три закрытые подсказки.
6. Закрытое `Решение`.
7. Закрытое `О задаче`.

В карточке нет:

- ссылки `← Все подборки`;
- browser-back инструкции;
- fallback-ссылки `Потерялись?`;
- `Учебной цели` или фразы `что тренируем`;
- `Готово, когда`;
- `Самопроверки`;
- инструкции, как открывать и закрывать подсказки;
- обязательной теории;
- test harness;
- диагностических флагов;
- подробных искусственных fixtures;
- полного повторения starter-кода в решении.

### 5.2 Условие

`Условие` — единственный видимый источник требований.

Оно:

- прямо говорит, что реализовать, исправить, разобрать или предсказать;
- включает всё обязательное наблюдаемое поведение;
- не объясняет педагогическую мотивацию;
- не содержит внутренних терминов Beads, GRACE, evidence, contract или
  preservation;
- не повторяется отдельным списком критериев после starter.

Для задачи, приближённой к реальной работе, условие может быть разбито на
последовательные обязательные этапы.

### 5.3 Starter-код

Starter содержит только код, необходимый для попытки.

Запрещены:

- тестовый runner внутри карточки;
- массивы диагностических сценариев, если они не являются данными задачи;
- флаги вида `allChecksPass`;
- намеренно раздутые error matrices;
- декоративная разметка и CSS;
- код, который существует только для демонстрации решения.

Один-два коротких входных примера допустимы, если без них невозможно понять
форму данных.

### 5.4 JavaScript и DOM

Для JavaScript-задачи по умолчанию публикуется один блок `javascript`.

Полный HTML-документ запрещён. В частности, в starter и solution не добавляются:

- `<!doctype html>`;
- `<html>`, `<head>` и `<body>`;
- `<style>`;
- `<script>`;
- подключение или импорт скрипта через HTML.

Если задача использует DOM и без разметки непонятно доступное окружение, перед
JavaScript разрешён отдельный минимальный HTML-фрагмент. Он содержит только
семантически необходимые элементы и считается данным условием, а не вторым
заданием.

### 5.5 TypeScript, HTML/CSS и React

- TypeScript: минимальный типовой контекст и изменяемая функция; без
  диагностического harness.
- HTML/CSS: только необходимый HTML-фрагмент и изменяемый CSS; без полного
  документа и декоративных стилей.
- React: один `src/App.tsx` по умолчанию. Несколько файлов разрешены только для
  задачи, приближённой к реальной работе, когда файлы представляют настоящие
  части мини-проекта.

`FILE:` обязателен только при нескольких реальных файлах.

## 6. Progressive disclosure

### 6.1 Подсказки

Сохраняются ровно три независимые закрытые подсказки:

1. `Подсказка 1 — куда смотреть`;
2. `Подсказка 2 — с чего начать`;
3. `Подсказка 3 — почти решение`.

Подсказки остаются короткими. Перед ними нет инструкции, объясняющей взрослому
пользователю, как пользоваться `<details>`.

### 6.2 Решение

`Решение` закрыто по умолчанию и содержит:

- итоговую функцию, обработчик, CSS-фрагмент или изменённый компонент;
- короткое объяснение ключевого решения;
- ожидаемый результат и простой способ ручной проверки.

Решение не повторяет:

- неизменённые fixtures;
- весь starter;
- окружающий HTML-документ;
- тестовый harness;
- файлы, которые не менялись.

Для нескольких настоящих файлов решение показывает только изменённые файлы.

## 7. Метаданные

`О задаче` остаётся закрытым и содержит пять полей:

- `Технология`;
- `Подборка`;
- `Формат`;
- `Сложность`;
- `Примерное время`.

Для обычных задач сохраняются значения формата:

- `Написать код`;
- `Исправить код`;
- `Разобрать код`;
- `Предсказать результат`.

Для нового класса добавляется значение:

- `Приближённая к реальной работе`.

Это значение описывает характер задания и не заменяет тематическую подборку.

## 8. Каталог

Создаётся новая cross-cutting collection page:

```text
collections/real-work/README.md
```

Видимый заголовок:

```text
Приближённые к реальной работе
```

Страница содержит только задачи с подтверждённым real-work форматом. Каждая из
них одновременно присутствует:

- ровно в одной тематической подборке;
- в `collections/real-work/README.md`;
- не более чем в одной interview collection.

Корневой README получает ссылку на новую подборку. Итоговый root contract
обновляется атомарно:

- сохраняются четыре текущих `##` блока;
- ссылка добавляется последним пунктом в `Подборки по направлениям` и явно
  описывается как отдельный практический формат, а не одиннадцатое направление;
- root содержит ссылки на десять thematic, три interview и одну real-work
  collection page.

Старая проверка ровно тринадцати collection pages заменяется проверкой ровно
четырнадцати.

## 9. Новая эталонная задача

### 9.1 Идентичность

Рабочее название:

```text
Список пользователей из API
```

Предлагаемый slug:

```text
users-api-list
```

Метаданные:

- Технология: `React/TypeScript`;
- тематическая подборка: `React: эффекты и жизненный цикл`;
- дополнительная подборка: `Приближённые к реальной работе`;
- Формат: `Приближённая к реальной работе`;
- Сложность: `Продвинутая`;
- Примерное время: `60 минут`;
- редактор: `https://vite.new/react-ts`.

Slug и точное тематическое положение подтверждаются implementation plan после
duplicate и collection-capacity review.

Предварительно выбрана подборка `React: эффекты и жизненный цикл`, потому что
основная работа задачи — синхронизация интерфейса с удалённым ресурсом и
состоянием запроса. Если duplicate review докажет другой основной предмет,
план обязан вернуть это как product decision, а не молча сменить collection.

### 9.2 API

Задача использует официальный DummyJSON Users API:

```text
https://dummyjson.com/docs/users
```

Релевантные контракты:

- `GET /users`;
- `limit` и `skip` для серверной пагинации;
- `GET /users/search?q=...` для серверного поиска;
- ответ содержит `users`, `total`, `skip`, `limit`.

Карточка фиксирует размер страницы `10`. Обычный запрос использует:

```text
/users?limit=10&skip=<offset>
```

Поисковый запрос использует:

```text
/users/search?q=<query>&limit=10&skip=<offset>
```

Поиск запускается отправкой формы, а не каждым нажатием клавиши. Это оставляет
серверный поиск и конкурирующие запросы частью задания, но не добавляет
неоговорённый debounce.

В карточке не копируется вся документация API. Условие содержит только
используемые endpoint и поля ответа и даёт ссылку на официальную документацию.

### 9.3 Последовательные требования

Все этапы обязательны:

1. Получить пользователей и вывести имя, email и аватар.
2. Добавить кнопки перехода назад и вперёд; вычислять доступность страниц через
   `total`, `limit` и `skip` и не отправлять запрос за границы списка.
3. Добавить серверный поиск через query parameter `q`.
4. При отправке нового поискового запроса возвращаться на первую страницу.
5. Показать отдельные loading, error и empty states.
6. Не показывать данные предыдущего запроса как результат нового поиска.

Этапы дают частичный сигнал прогресса: незавершённая попытка всё равно
показывает, какие продуктовые требования кандидат успел реализовать.

### 9.4 Starter и решение

Starter:

- один минимальный `src/App.tsx`;
- без готовой архитектуры;
- без CSS;
- без тестов;
- без заранее реализованного data-fetching hook.

Кандидат самостоятельно выбирает компоненты и структуру состояния.

Решение может разделить код на несколько оправданных компонентов или hook, но
публикует только необходимые изменённые файлы и не добавляет декоративный UI.

## 10. Миграция двадцати существующих карточек

Каждая карточка проходит отдельный content review:

1. Зафиксировать текущее центральное действие.
2. Удалить служебную педагогическую формулировку.
3. Удалить второстепенные требования, если они образуют отдельную задачу.
4. Сократить starter до рабочего контекста.
5. Удалить harness и подробные fixtures.
6. Сократить solution до изменяемого фрагмента.
7. Синхронизировать название, время, формат, тематическую и interview
   membership.
8. Проверить карточку в целевом редакторе.

Текущие двадцать карточек мигрируют как сфокусированные. Если review докажет,
что конкретная карточка по сути является самостоятельным 45–60-минутным
мини-проектом, её нельзя молча оставить большой: требуется отдельное
пользовательское решение о переводе в real-work формат.

## 11. Verification

### 11.1 Структурные проверки

Для каждой карточки проверяются:

- точный порядок: title, editor instruction, `Условие`, starter, три hints,
  `Решение`, `О задаче`;
- отсутствие `Учебной цели`, `Готово, когда` и `Самопроверки`;
- отсутствие back/fallback navigation;
- ровно три закрытых hint details;
- закрытые `Решение` и `О задаче`;
- пять точных metadata labels;
- отсутствие полного HTML-документа и `<script>` в JavaScript-задачах;
- отсутствие известных harness-маркеров;
- отсутствие неоправданного multi-file split.

### 11.2 Содержательные проверки

Reviewer подтверждает:

- у сфокусированной задачи одно центральное действие;
- условие однозначно;
- starter достаточен, но не решает задачу;
- solution выполняет условие и не дублирует окружение;
- три подсказки образуют реальную прогрессию;
- формат и время соответствуют фактическому объёму.

### 11.3 Runtime и browser evidence

- JavaScript и TypeScript проверяются в заявленном online editor.
- DOM и React проверяются в браузере.
- HTML/CSS проверяется вручную в браузере; automated CSS assertions запрещены.
- DummyJSON-задача проверяет список, pagination, search, page reset, loading,
  error, empty state и stale-response protection.
- Loading проверяется с browser network throttling. Error проверяется в
  диагностической копии временной подменой endpoint или browser offline mode;
  эта подмена не публикуется в starter. Empty state проверяется поиском без
  результатов.
- Недоступный обязательный editor или DummyJSON означает `BLOCKED`, не `PASS`.
- Временный harness разрешён только агенту как диагностический инструмент и не
  публикуется в карточке.

### 11.4 Rendered audit

После полной миграции проверяются:

- root hub;
- десять thematic, три interview и одну real-work collection page;
- все двадцать одна task page;
- закрытое начальное состояние details;
- editor links;
- collection memberships;
- отсутствие старого boilerplate в GitHub-rendered Markdown.

Итоговый инвентарь содержит 36 страниц: root, 14 collections и 21 task card.

- `AGENTS.md`;

- `docs/task-validation-policy.md`;
- двадцать существующих `tasks/*/README.md`;
- новую `tasks/users-api-list/README.md`;
- тематические и interview collections;
- `collections/real-work/README.md`;
- корневой `README.md`;
- `docs/requirements.xml`;
- `docs/technology.xml`;

- `docs/verification-plan.xml`;
- `docs/knowledge-graph.xml`;
- `docs/operational-packets.xml`;
- Beads candidate, migration, wave и rendered evidence.

Исторические completed phases не переписываются. Implementation plan добавляет
новые последовательные redesign phases и gates. Ни один будущий факт не
помечается implemented до соответствующей student-facing волны.

## 13. Ошибки, которые останавливают миграцию

Миграция останавливается, если:

- условие нельзя свести к одному действию без изменения смысла;
- минимальный starter не позволяет выполнить задачу;
- удалённый fixture на самом деле является обязательным входом;
- solution требует скрытого окружения;
- задача заявлена сфокусированной, но фактически остаётся мини-проектом;
- real-work membership противоречит времени или формату;
- DummyJSON contract изменился или обязательный endpoint недоступен;
- title, duration, editor или collection membership расходятся;
- GitHub неожиданно рендерит code fences или details;
- обязательное browser/editor evidence недоступно.

## 14. Acceptance

Дизайн готов к planning, когда:

- пользователь письменно одобрил эту спецификацию;
- Beads issue содержит ссылку на утверждённый commit;
- self-review не находит placeholder, противоречий или двусмысленности;
- implementation plan может разложить работу на атомарные последовательные
  волны без конкурентного изменения shared artifacts.

Реализация не означает финальное принятие библиотеки. Decision
`frontend-livecoding-tasks-kln-final-acceptance` и top-level story остаются
открытыми до нового полного rendered audit и явного ответа пользователя.
